# 390px mobile-overflow evaluation — 2026-10-28 (audit Stage 3, UX-01)

## Method (honest about what this is)

- Local headless Chromium via Playwright on this VM — NOT the user's
  live browser, NOT production. Local dev server (`unified_app.py`,
  port 5001), viewport 390×844.
- Reusable script: `scripts/eval_overflow_390.py` (takes `--base` +
  `--out`; records per page: HTTP status, `documentElement.scrollWidth`
  vs viewport width, and up to 10 elements whose boxes extend past the
  viewport edge).
- Two runs: BEFORE (base.html with the guard stashed away — pre-guard
  state) and AFTER (guard restored + standalone copies added + the
  roadmaps grid fix). Raw reports: `overflow-390px-before.json`,
  `overflow-390px-after.json` (this folder).
- What counts as a defect here: `scrollWidth > viewport` (a real
  horizontal scrollbar) OR a content element cut off at the edge.
  Elements inside an `overflow-x: auto` / `overflow: hidden` container
  (scrollable tables, clipped marquees, fixed decorative glows) are
  reported as overhangs but are NOT defects — the report names them so
  the distinction is auditable, not hidden.

## The one real defect: roadmaps skill-card grid

- Cause: `templates/roadmaps.html` hardcoded the skill-card grid to
  `grid-template-columns:repeat(3,1fr)`. At 390px each card is ~120px
  wide, but a card holds a checkbox + skill name + a `width:auto`
  level `<select>` (sized to "Intermediate"), so 9 selects overflowed
  their cards at the viewport edge.
- Fix (same file): grid given the class `gap-skills-grid` with
  `repeat(3,1fr)` on desktop and `1fr` below 640px; the inline
  3-column style removed. Re-evaluation confirms the selects no
  longer overhang (only the decorative cursor glow remains).
- Lock test: `tests/test_mobile_overflow_guard.py::test_roadmaps_skill_grid_collapses_on_narrow_screens`.

## What the guard is (and is not)

- Added to `templates/base.html` (inherited by 47 templates) and to
  all 32 standalone full-page templates — 33 `<html>` templates total,
  verified by grep (0 hardcoded `<html lang="en">` remain; every page
  carries `max-width: 100%` media/table rules, `pre` horizontal
  scrolling, and `html, body { overflow-x: clip }`).
- The guard changed NOTHING on the evaluated pages (before/after
  scrollWidths identical) — it is a preventive safety net for
  unevaluated pages, not a fix for measured breakage. That is the
  honest reading: the audit's "can overflow" was a risk statement, and
  the measured hub pages were already contained.
- Lock tests: `tests/test_mobile_overflow_guard.py` (guard present
  everywhere, no hardcoded `lang="en"`, roadmaps grid rule).
